# Design

## Context

管理端已有统一的模块页面容器、表格容器、失败重试和原因弹窗，学生目录可以直接复用这些交互。Spring 已提供学生列表、详情、历史和启用/禁用接口，接口路径与响应字段稳定，因此本变更不新增 API、不新增数据表。

现状中有两处需要在本次收敛：

- 学生列表为每个学生单独查询一次在养领养数，学生数量增加时会产生 N+1 查询。
- 禁用/启用原因的 `@Size` 校验发生在去除首尾空白之前，带空白填充的短原因可能通过参数校验。

`apps/web` 目前没有消费学生管理接口，本变更不涉及它；也没有跨应用运行时代码需要抽到共享包。

## Goals / Non-Goals

**Goals:**

- 用真实 `/students` 页面替换占位页，覆盖列表、筛选、分页、详情、历史分组和账号启停。
- 复用现有 Spring 接口和 admin 现有页面组件，不引入新依赖。
- 消除学生列表的 N+1 活跃领养计数，并让原因长度校验与前端一致。
- 为学生接口补充服务层和契约测试，保证列表、详情、历史和状态操作可回归。
- 保持 Oxc 为唯一 lint/format 工具链，不修改 tsconfig、Vitest 配置、覆盖率 include 或 Turbo 输入。

**Non-Goals:**

- 不提供删除学生、编辑学生资料、调整积分、批量操作或导出。
- 不新增服务端筛选、分页或排序参数；本变更使用客户端筛选和分页。
- 不改变认证流程、角色边界、数据库结构、`apps/web` 或共享包。
- 不批量改造历史接口中“最新凭证”的逐条查询；本次只处理列表 N+1。

## Decisions

### 1. 复用现有接口，前端完成筛选与分页

数据流：

```text
/students
  |
  +--> GET /api/v1/admin/accounts            (全部 STUDENT，注册时间倒序)
  |       |
  |       +--> 客户端关键词/院系/状态/日期筛选 + 每页 10 条
  |
  +--> 查看详情
          |
          +--> GET /api/v1/admin/accounts/{id}
          +--> GET /api/v1/admin/accounts/{id}/history
          |
          +--> 禁用/启用
                  |
                  +--> POST /api/v1/admin/accounts/{id}/disable
                  +--> POST /api/v1/admin/accounts/{id}/enable
```

列表一次请求加载全部学生，页面在本地维护原始数组和已应用的筛选条件，筛选结果由二者派生。学生数据规模当前适合客户端处理，也与领养、反馈等既有页面保持一致。

备选方案是新增服务端筛选和分页；但注册日期筛选仍需客户端参与，且会扩大接口契约和测试范围，本变更不采用。

### 2. 页面由列表页和详情抽屉组成

- `StudentsPage` 负责列表、筛选、分页、加载失败和刷新；使用现有 `ModulePage`、`AdminTable` 和分页组件。
- `StudentDetailDrawer` 负责基础资料、五个历史标签页和账号状态操作；抽屉内使用普通 `Table` 而不是 `AdminTable`，避免页面高度计算与抽屉滚动冲突。
- `labels.ts` 集中维护账号状态、领养/打卡/任务/订单状态、来源类型和中文空态文案。
- `accounts.ts` 扩展为完整的学生 API 客户端，并保留现有 `listStudents()` 无参调用，避免影响领养、反馈、积分和奖励页面。
- 禁用/启用直接复用现有 `ReasonModal`；其前端已按去除空白后的 5–200 字校验。

### 3. 详情与历史独立加载

打开抽屉时并行请求详情和历史，但分别维护 loading、error 和 data：

- 详情失败只影响基础资料区域，历史仍可展示。
- 历史失败只在历史区域显示错误和重试，基础资料保持可见。
- 打开另一名学生时清空上一名学生的数据，避免短暂显示错配信息。
- 状态操作成功后，用响应替换当前详情和列表中的对应学生；列表的筛选结果由原始数组派生，因此状态筛选会自动重新计算。若当前页超出范围，再回退到最后一页。

### 4. 批量计算在养领养数

在领养仓储端口增加按学生 ID 集合和状态分组的计数查询，持久化适配器用一次 `GROUP BY student_id` 查询返回每个学生的数量。`AccountService.adminList` 先取学生列表，空列表直接返回；否则一次取计数并映射到 `AccountView`。详情和状态操作仍使用单学生计数。

备选方案是保留逐学生计数；它在数据量增长时不可接受。另一个备选是把计数放进账号表冗余字段；会引入跨模块一致性成本，不采用。

### 5. 原因长度在后端按去空白后的值校验

`StatusRequest` 保留非空校验，移除只按原始字符串判断的固定长度校验；`AccountService.setStatus` 去除首尾空白后检查 5–200 字，不合法时返回 400 `INVALID_REQUEST`，并用去除空白后的原因写审计记录。前端 `ReasonModal` 仍先做同样的客户端校验，后端作为最终边界。

备选方案是新增自定义 Bean Validation 注解；为一个字段增加校验基础设施不划算，服务层校验更直接。

### 6. 错误与空态分层处理

- 列表主请求失败：整块显示 `LoadFailure` 和重试。
- 筛选无结果或没有学生：显示“暂无学生”空态，保留筛选区。
- 详情失败：基础资料区域显示错误和重试。
- 历史失败：历史区域显示错误和重试。
- 状态操作失败：原因弹窗保持打开并保留输入；404 时关闭弹窗并刷新列表。
- 401 交给现有会话处理，不在页面重复提示。

### 7. 响应式与可访问性

列表在窄屏使用 `AdminTable` 的内部横向滚动，筛选区自动换行；详情抽屉在移动端占满宽度，历史标签可横向滚动；原因弹窗在 320px 下完整可用。账号状态以“正常/已禁用”文本加颜色表达，标签页和操作按钮保持键盘可操作，亮暗主题沿用 antd token。

### 8. 测试与验证

- admin API 测试：学生列表、详情、历史、启用/禁用的路径、方法和请求体。
- admin 页面测试：列、筛选、分页、空态、失败重试、详情、五个历史标签、状态操作确认与失败保留。
- 路由测试：`/students` 不再渲染占位页。
- 后端服务测试：列表只调用一次批量计数、空列表不查计数、原因去除空白后校验。
- 后端契约测试：学生列表/详情/历史的 401、403、200、404，以及启用/禁用的 200、400、404。
- 持久化适配器测试：分组计数查询按学生 ID 集合和状态调用，空集合短路。
- 验证命令：`./mvnw verify`（`../backend`）、`pnpm --filter admin lint`、`pnpm --filter admin check-types`、`pnpm --filter admin test`；完成后从仓库根目录运行 `pnpm verify`。

## Risks / Trade-offs

- [客户端筛选和分页会一次加载全部学生] → 当前校园规模可接受；若学生数量显著增长，再以独立变更增加服务端分页和筛选。
- [历史接口返回一个学生的全部记录] → 首版按单学生加载并在客户端分页；数据量增长后再考虑服务端分页。
- [历史接口仍存在逐条查询最新凭证] → 本变更不扩大范围；单学生历史通常有限，列表 N+1 是更直接的性能风险。
- [批量计数需要处理空学生列表和未命中学生] → 空集合直接返回空映射，未命中学生默认计数为 0。
- [前后端都校验原因长度，可能产生重复提示] → 前端负责即时反馈，后端负责最终边界；两者使用同一“去空白后 5–200 字”规则。
- [列表按注册时间倒序但未增加 ID 兜底] → 同一时间的顺序不构成业务依赖；若后续需要稳定顺序，再单独补充排序规则。

## Migration Plan

1. 先发布后端加固；接口路径和响应字段不变，现有 admin 页面不受影响。
2. 发布 admin 页面，`/students` 从占位页切换为真实页面。
3. 回滚时只需回退 admin 路由和页面；后端加固对既有调用保持兼容，无需数据库回滚。
4. 无数据迁移，无环境变量或部署配置变更。
