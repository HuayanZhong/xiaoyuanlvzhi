# Design

## Context

`/points/rules` 当前仍由 `PlaceholderPage` 渲染，但 Spring 已经提供规则列表、规则更新、全量流水和人工调整接口。养护审核和任务审核已经会写入 `point_ledger`；积分规则种子为 `CARE_CHECKIN` 与 `ECO_TASK` 两条，初始为 0 分、停用。管理端还缺少页面入口和必要的服务端校验。

本设计建立在现有 admin 列表/抽屉模式上：`ModulePage` 提供面包屑和内容区，`Tabs` 组织两个 tab，`Table` + 客户端筛选 + 每页 10 条与现有模块保持一致；Spring 仍是认证与角色边界。

## Goals / Non-Goals

**Goals:**

- 在 `/points/rules` 提供可操作的规则配置、全量流水查询和人工调整。
- 明确 `CARE_CHECKIN` 与 `ECO_TASK` 的积分来源语义，避免页面配置与审核发放不一致。
- 人工调整具备学生范围限制、余额校验和重试幂等。
- 复用现有账号目录、错误信封、加载失败和移动端模式。

**Non-Goals:**

- 不实现奖励商品、兑换订单、学生管理、工作台、统计和资讯管理。
- 不新增积分规则种类，不实现规则删除或历史版本页面。
- 不引入服务端分页、导出或复杂报表；首版继续客户端筛选和分页。
- 不修改养护/任务审核的积分来源规则；本变更只提供配置入口和接口加固。

## Decisions

### D1: 一个页面、两个 tab

`/points/rules` 同时承载“积分规则”和“积分流水”。导航已经只有“积分规则与流水”一个入口，拆成两个路由会增加导航和深链复杂度。默认选中“积分规则”，与用户进入配置页的预期一致；流水通过 tab 切换，页面标题保持“积分规则与流水”。

替代方案是拆成 `/points/rules` 与 `/points/ledger` 两个路由。优点是每个页面更轻；缺点是现有导航需要新增一项或修改产品信息架构，且两个页面共享账号目录和规则数据，收益不足。

### D2: 规则编辑使用抽屉表单

规则只有启用状态、积分、频控周期和次数四个字段，使用与任务表单一致的右侧 `Drawer`，移动端全宽。`ECO_TASK` 不展示可编辑积分，只显示“由任务配置决定”；`CARE_CHECKIN` 展示积分输入，并在表单下方说明“规则积分优先，品种积分兜底”。

频控周期选择“不限 / 每日 / 每周”。选择“不限”时清空并禁用次数输入；选择每日或每周时次数必填且至少为 1。这样页面不会产生后端不执行的 `PER_TASK` 配置。

### D3: `ECO_TASK` 的规则积分固定为 0

任务审核已经按 `task.pointsPerPerson` 发放积分，`ECO_TASK` 规则的 `points` 当前没有参与发放。首版将规则积分明确为 0，服务端对大于 0 的 `ECO_TASK` 积分返回 400，页面不展示可编辑积分；`ECO_TASK` 规则只控制启用状态和每日/每周频控。`CARE_CHECKIN` 启用时积分必须大于 0；停用时允许保留 0，避免种子规则在停用状态下无法保存。

替代方案是让全局 `ECO_TASK` 积分覆盖任务配置。该方案会与“每个任务配置自己的每人奖励积分”冲突，并可能追溯改变已发布任务的奖励，因此不采用。

### D4: 首版移除 `PER_TASK`

`PER_TASK` 当前会被接口接受，但 `enforceFrequency` 对它直接返回，属于“可配置但不生效”的假选项。首版只保留不限、每日、每周；服务端对 `PER_TASK` 返回 400 `FREQUENCY_PERIOD_INVALID`。对历史数据中可能存在的 `PER_TASK` 行，规则列表按“不限”展示，下一次编辑时写回空频控；不新增 Flyway 迁移。

替代方案是补全“每任务”频控。任务参与记录本身已经保证同一任务只发一次，养护打卡也没有“任务”上下文；实现该语义需要重新定义业务口径，超出本变更范围。

### D5: 流水学生资料由账号目录关联

`LedgerView` 已包含 `accountId` 和 `studentEmail`。页面并行加载现有 `GET /api/v1/admin/accounts`，按 `accountId` 关联姓名、学号和当前余额；账号目录失败时学生列回退邮箱，流水仍可查看。这样不修改流水 DTO，也不新增跨域字段。

替代方案是在后端 `LedgerView` 直接补姓名和学号。该方案减少一次前端关联，但会扩大 API 变更并重复账号目录职责；首版数据规模有限，客户端关联与领养管理现有做法一致。

### D6: 人工调整使用客户端请求键

`AdjustRequest` 增加可选 `requestId`，页面在首次提交时用 `crypto.randomUUID()` 生成，并在同一表单内容的失败重试中复用；用户修改学生、方向、积分或原因后清空请求键，下一次提交生成新键。服务端以 `ADJUSTMENT:{requestId}` 作为流水键：重复同内容请求返回首次流水，不重复改余额或写审计；同一键对应不同内容返回 409 `IDEMPOTENCY_KEY_REUSED`。

替代方案是只在前端禁用提交按钮。该方案无法覆盖请求已到达服务端但响应超时的场景，因此服务端仍需要幂等键。

### D7: 调整目标必须是学生

人工调整接口虽然只有管理员可调用，但 `accountId` 仍可能指向管理员账号。服务端在扣加积分前校验目标账号角色为 `STUDENT`，否则返回 404 `STUDENT_NOT_FOUND`；页面只从学生目录选择目标。替代方案是返回 403，但 404 可避免在错误信息中暴露管理员账号的存在。

### D8: 规则更新记录审计事件

规则更新使用现有 `operation_logs` 记录 `POINT_RULE_UPDATE`，`entityType=POINT_RULE`、`entityId=规则 ID`，原因字段保存更新前后的积分、频控、周期和启用状态。现有状态字段长度不足以承载完整配置，因此不修改表结构，使用原因字段记录快照。

替代方案是不记录审计。规则修改会直接影响后续审核发放，留下操作人和前后值更利于排查；实现成本低。

### D9: 流水排序与页面加载

`GET /api/v1/admin/points/ledger` 在现有创建时间倒序基础上增加 ID 倒序，保证同一时间戳下的稳定顺序。页面首次进入并行加载规则、流水和账号目录；流水与规则各自维护加载/失败状态，单列表失败不阻塞另一个 tab。首版一次加载全部流水，客户端筛选和分页，与任务/养护页一致。

替代方案是增加服务端分页和筛选参数。当前接口没有这些参数，且页面需要跨账号目录关联；首版继续客户端处理，后续数据量增长时再独立变更。

### D10: 账号余额类型扩展

`apps/admin/src/api/accounts.ts` 的 `StudentView` 增加 `pointsBalance: number`。后端 `AccountView` 已经返回该字段，前端只是补类型并用它做调整预览，不需要修改 Spring 响应。

## Risks / Trade-offs

- **流水全量加载在数据量大时变慢** → 首版接受；接口保留稳定排序，后续可加服务端分页。
- **账号目录与流水之间存在短暂不一致** → 调整成功后同时刷新流水和账号目录；账号目录失败时回退邮箱并给出提示。
- **`PER_TASK` 移除影响直接调用接口的客户端** → 在 proposal 标记 BREAKING；当前没有已接入的管理端页面，发布说明中注明只接受不限、每日、每周。
- **历史 `PER_TASK` 数据仍在库中** → 规则列表按不限展示，后续编辑时清理；审核频控本来就不执行该周期，行为不变。
- **请求键被客户端复用或省略** → 页面每次表单意图生成新键并复用重试；省略时服务端生成新键，保持旧客户端可用但不具备幂等。
- **规则更新与审核并发** → 规则读取与更新没有额外锁；审核使用当前已生效规则，最后写入的规则影响后续审核。首版接受，不引入规则版本表。
- **审计原因字段被截断** → 只记录四个短字段的快照，控制在 `reason` 500 字以内。

## Migration Plan

1. 先部署 Spring：放宽 `ECO_TASK` 的积分校验、拒绝 `PER_TASK`、增加调整幂等和目标角色校验，并补充测试；不新增数据库结构。
2. 再发布 admin：替换 `/points/rules` 占位页，接入新接口和账号余额字段。
3. 回滚时先回滚 admin，再回滚 Spring；历史 `PER_TASK` 数据不迁移，接口按不限返回，避免不可逆的数据修改。
4. 验证：后端 `./mvnw verify`，admin `pnpm --filter admin test`、`lint`、`check-types`，根目录 `pnpm verify`；再用真实接口和浏览器完成规则更新、流水筛选、人工调整和 320px 检查。
